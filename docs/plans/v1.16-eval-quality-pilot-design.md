# Design: check outcome quality beyond the original eval case

Status: DRAFT
Mode: Feature
Date: 2026-11-22

## Problem

An agent can satisfy an evaluation and still deliver a result that fails in ordinary use. The next change should establish a small, repeatable check for that discrepancy in the shared harness.

## Evidence

- The routing grader passed the offline-verification skill alone and returned `extra harness skill loaded` when systematic debugging was also observed. That is the specified behavior of an isolated routing case. It cannot tell whether the extra skill helped a task with an actual failure.
- A temporary-project CLI replay exposed a real coverage gap. Revision `92e3bca` rejected both a wrapped decision and a wrapped decision followed by a nested list. The initial fix `83713c5` accepted only the first input. Follow-up `3cbb76b` accepted both. All three rejected a record missing a required field.

## Approaches considered

1. Relax the exact routing rule now. This is a small code change. The available evidence concerns an isolated routing test, so it gives no basis for a suite-wide policy change.
2. Replay one historical defect through the normal CLI with ordinary input variations and an invalid control. This gives executable evidence about a quality check with a small and reversible scope. The public historical scenario supports calibration and regression verification.
3. Compare fresh patches made with two versions of the harness guidance. This would measure agent behavior directly. It needs multiple matched tasks and runs per condition to distinguish a guidance effect from run variance.

## Recommended approach

Start with the historical CLI replay. If it distinguishes the initial fix from the follow-up, add one instruction to the existing eval skill for artifact evaluations. Keep task outcomes and process signals visible individually, and take unfamiliar ordinary inputs from the documented behavior before comparing results.

## Decisions

- D1: Use the historical decision parser fix to calibrate outcome evaluation -- why: the first fix passed the original reproducer while rejecting a normal variant, and there is a later corrective revision with the same CLI -- by: observed -- paths: lib/decisions.py
- D2: Keep changes to isolated routing cases outside this pilot -- why: skill selection and correctness of a delivered artifact have different evidence -- by: observed -- paths: evals/run.py skills/eval/SKILL.md

## Success criteria

The same CLI matrix reports an input that distinguishes the initial fix and the follow-up, and confirms that malformed input is still rejected. The report shows each outcome and the scope of the conclusion. A published regression case is available to both arms in any later experiment, so a fresh comparison needs new task variations.
