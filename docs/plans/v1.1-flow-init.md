# v1.1-flow-init: init skill, roadmap flow, one instruction file per project

Status: implemented (Codex; reviewed by Claude)

## Context
Three gaps found after v1. The user keeps asking "what is next, go on" because the order of work lives only in a private Claude plan file and the global rules stop at every milestone. The template and decision format exist, but nothing fills them for an existing repository (the role init-deep plays in OmO). Claude Code now reads a project's AGENTS.md directly, so the one-line project CLAUDE.md is redundant. Success: `scripts/check` passes, `bin/doctor --project .` prints no WARN or FAIL, and the new live evals pass.

## Decisions
- D1: The order of work lives in `docs/plans/roadmap.md`, one line per spec; an item counts as approved when its spec says `Status: approved`, so the roadmap adds no status field of its own -- why: a second approval field would drift from the spec, and both tools can read a file in git while the old plan file was private to Claude -- by: user -- paths: docs/plans/roadmap.md global/AGENTS.md
- D2: The global rules stop at a milestone only when the next item has no approved spec; the list of actions that need approval is unchanged -- why: the user approved whole plans yet was asked again at every step -- by: user -- paths: global/AGENTS.md
- D3: A `next` skill is not built; it is added only if the flow evals fail reproducibly with the rules alone -- why: finding the next item is a lookup, and the harness adds machinery only for failures that reproduce (v1-memory#D2) -- by: user
- D4: The `init` skill fills the harness template for an existing repository: a root AGENTS.md only, decisions moved into the record format, and a `Checked at <sha>` line so a rerun rechecks only rows whose paths changed -- why: the value is the constraints and their reasons, not a description of the code, and a recorded commit makes reruns cheap without an index -- by: user -- paths: skills/init/SKILL.md bin/doctor
- D5: OmO init-deep is used for ideas only; no text is copied -- why: its Sustainable Use License allows only non-commercial distribution, which does not fit an MIT repository -- by: observed -- paths: SOURCES.md
- D6: Projects keep instructions in AGENTS.md only; the harness no longer adds a project CLAUDE.md -- why: Claude Code 2.1.322 loaded a project AGENTS.md with no CLAUDE.md present (tested with file tools disabled) -- by: user -- paths: README.md templates/AGENTS.md
- D7: Hooks and their library code stay on Python 3.9 -- why: the user left the call to the agent; lifting it would make every commit fail on machines without a newer Python, against the multi-machine goal, and nothing needs newer syntax; revisit when the macOS system Python reaches 3.10 -- by: observed -- paths: lib git/hooks

- D8: The table check warns only when a file under a row was removed or a new top-level folder has no row; ordinary edits under a row pass -- why: warning on every edit fired on the first ordinary commit after the refresh, and a warning that always fires gets ignored -- by: observed -- paths: bin/doctor tests/test_doctor.py

## Interfaces
§1 `bin/doctor --project <path>` additions (existing lines unchanged):
- In the project AGENTS.md section `## Sources of truth`, for each table row, every backticked token in the second column that contains no `<`, `>` or `*` is a path relative to the project; a missing one prints `WARN stale table: <path> (row "<first column>")`.
- A line `Checked at <sha>` in that section: when `<sha>` is not a commit, `WARN table check: unknown commit <sha>`; otherwise list `git diff --name-only <sha>..HEAD`, and when any changed file lies under a path from the second column, print `WARN table check: <n> changed path(s) under table rows since <sha>; rerun the init skill` naming up to five; else `PASS table check: no table path changed since <sha>`. No `Checked at` line: `WARN table check: no Checked at line (run the init skill)`.
- With no AGENTS.md, these checks are skipped (the existing WARN covers it).

## Appendix A: skills/init/SKILL.md

````markdown
---
name: init
description: "Fill or refresh a repository's AGENTS.md from the bell-harness template by reading the code: where to look for each kind of change, the constraints there and the decisions behind them, plus the commands to check work. Use when the user says \"init\", \"init-deep\", \"이 저장소 정리해줘\", \"AGENTS.md 만들어줘\", when a repository has no AGENTS.md or one that does not follow the template, or when bin/doctor reports a stale table."
---

# Init

Write down what an agent needs before changing this repository and cannot see in the code: which constraints apply where, and why. The result is one root `AGENTS.md` in the harness template shape, decision records in `docs/plans/`, and a commit marker that makes the next refresh cheap. Facts the code already shows, such as a directory listing or generic advice, stay out, because every line is read in every session.

## First run

1. **Read what exists.** The current `AGENTS.md`, `CLAUDE.md`, `README.md`, `docs/`, `tasks/lessons.md`, any decision log or ADR, the build and test configuration, and `git log --oneline -50`. Keep every statement that is still true.
2. **Explore.** Find entry points, the single check command, test layout, conventions that differ from the language default, and warnings in comments or docs ("do not", "deprecated", "must stay"). For a large repository, give each top-level directory to a fresh subagent with a fixed brief (entry points, conventions, warnings, commands) and treat their reports as claims to spot-check against the code.
3. **Collect reasons.** For each constraint, find why it exists: a spec, a decision log, a commit message, an issue. Move each one into a `## Decisions` line in the relevant spec under `docs/plans/` (create `docs/plans/decisions.md` when no spec fits): `- D<n>: <decision> -- why: <reason> -- by: user|observed -- paths: <paths>`. Use `user` only when the source shows the user decided it. When no reason can be found, write the constraint without a decision id and list it under open questions in your report rather than inventing one.
4. **Fill the template.** Use the headings of the harness `templates/AGENTS.md`. In `## Sources of truth`, write one row per kind of change: task, the files to look at, the constraint and its decision id. Keep the file under about 100 lines. Edit an existing `AGENTS.md` in place rather than rewriting it.
5. **Mark the check.** Under the table write `Checked at <short sha of HEAD>`.
6. **Leftovers.** When a project `CLAUDE.md` holds only `@AGENTS.md`, or content you merged into `AGENTS.md`, propose deleting it; Claude Code reads `AGENTS.md` directly. Delete only after the user agrees.
7. **Verify.** Run `bin/doctor --project .` from the harness (or the project's own check) and fix every WARN you caused. Then report the rows you wrote, the decisions you moved, and the constraints without a known reason.

## Refresh

When `Checked at <sha>` exists, run `git diff --name-only <sha>..HEAD`. Recheck only the rows whose paths changed and any new top-level area, update those rows and decisions, and move the marker to the new HEAD. When nothing under the table changed, say so and change nothing.

## Scope

One root `AGENTS.md`; no per-directory files. Commit through the normal hooks, or leave the changes for the user to review when the repository restricts commits.
````
