# v1.12-doctor-check-speed: reduce repeated diagnostic test setup

Status: approved

## Context

A local four-worker `scripts/check` run passed 95 tests in 68.845 seconds wall time. The `test_doctor` suite ran for 67.746 seconds, near the entire 67.937-second runner time. The other heavy suites were `test_setup` at 48.832 seconds and `test_evals` at 30.417 seconds. These are overlapping suite times from one run, not additive or a portable speedup claim.

## Decisions

- D1: Optimize test preparation before changing the parallel runner -- why: all 14 diagnostic tests currently install into independent temporary homes, and installation invokes doctor before the tests invoke it again -- by: observed -- paths: tests/test_doctor.py tests/test_setup.py bin/setup scripts/check
- D2: Reduce repeated fixture setup and require a ten percent median improvement -- why: the user approved all four recommended roadmap options -- by: user

## Scope

- Begin with `tests/test_doctor.py`. For tests exercising only project history or document checks, use the existing temporary fixture without a full installation where possible. Use the full install fixture for tests about links, previous roots, installation diagnostics and restoration. Retain an install-to-doctor integration check.
- If compact setup is still a major cost, prototype a smaller working-tree fixture in `tests/test_setup.py`. Copy the files actually consumed by initialization and diagnosis. Keep a full working-tree integration check. Preserve independent home directories, Git configuration and fixture mutations. Benchmark this experiment separately from the first.
- Keep `scripts/check`, its worker count and its guard in the measurement scope for comparison only. Do not add a dependency, change CI settings, substitute committed HEAD for changed runtime files, or skip any diagnostic case.

When splitting or reshuffling tests is considered, preserve the meaning of class and module fixtures. [Python 3.9 unittest fixtures](https://docs.python.org/3.9/library/unittest.html#class-and-module-fixtures)

## Acceptance tests

1. Compare the same 95 test IDs and verdicts, counting any new guard regression independently. Full install, moved-repository, existing diagnostic and fake-home guard cases still execute.
2. Run at least three alternating baseline and candidate measurements at the same worker count and environment. Report each sample, the median and the slowest suites. Keep a change only if it improves median full wall time by at least 10 percent and preserves coverage, or return an inconclusive result for review.
3. `scripts/check` prints `GUARD: real home unchanged`. Measure serial once as a compatibility check if test organization changes.
